1. What this project does (in plain English)

Imagine you want to start a small phone-service company. You want your customers to be able to:

  • Sign up on your website
  • Buy a SIP trunk (a virtual phone line)
  • Buy a phone number (a DID)
  • Make phone calls from their computer or office equipment
  • Receive phone calls on that number
  • Pay you per minute they use

You don't own the actual phone network — you partner with a carrier (in our case Synchrovox) who connects to the real telephone system. Your software sits in the middle: it authenticates your customers, controls how many calls they can make at once, tracks usage, and routes their calls to the carrier.

That whole platform is SIPaaS — "SIP as a Service." You're selling the ability to make phone calls without your customers needing to talk to a telecom carrier directly.

The simplest analogy

Think of yourself as an internet phone reseller. The carrier (Synchrovox) is the wholesaler who has the real connection to the phone network. You buy minutes from them at a wholesale rate, add your own software for billing and management, and sell phone service to your customers at a retail rate.

4. How a single call travels — step by step

You click Call Now in the browser with destination 9142436879. Here's exactly what happens.

Step 1: Browser-side SIP setup

  1. Your browser already has the JsSIP JavaScript library loaded.
  2. JsSIP opens a WebSocket connection to Asterisk at ws://localhost:8088/ws.
  3. Browser sends a SIP REGISTER message identifying as webrtcuser.
  4. Asterisk challenges with 401 Unauthorized; browser re-sends with digest-auth signature.
  5. Asterisk responds 200 OK — browser is now "registered."

Step 2: Browser dials the number

  1. You enter 9142436879 and click Call. Browser dispatches a sipaas:call event.
  2. BrowserPhone component picks it up, calls makeCall(dest).
  3. JsSIP sends a SIP INVITE over the WebSocket to Asterisk: 
    INVITE sip:9142436879@localhost SIP/2.0
From: webrtcuser  To: 9142436879  ...
SDP: audio offer with ICE candidates

Step 3: Asterisk runs the dialplan

  1. Asterisk receives the INVITE; pattern matches _[6-9]XXXXXXXXX (10-digit Indian mobile).
  2. Dialplan: 
    Set(CALLERID(num) = 00919240292847)        ; our caller ID
Set(DNIS = 0 + 9142436879 = 09142436879)   ; Synchrovox dial format
Dial(PJSIP/09142436879@synchrovox-trunk, 30, tTo)

Step 4: Asterisk → Synchrovox

  1. Asterisk sends a SIP INVITE over plain UDP to 20.193.182.13:5060.
  2. Synchrovox challenges with 401; Asterisk re-sends with digest using user/password (synchrovoxai_new.com / 1kdu9sr0a3w).
  3. Synchrovox routes the call to the Indian PSTN; customer's phone starts ringing.
  4. When customer answers, Synchrovox sends 200 OK back to Asterisk.
  5. Asterisk relays 200 OK back to your browser over the WebSocket.

Step 5: Audio starts flowing both ways

  1. Browser sends mic audio as encrypted RTP (DTLS-SRTP) to Asterisk on UDP 16000-16100.
  2. Asterisk decrypts and re-sends as plain RTP to Synchrovox.
  3. Synchrovox converts and sends voice over PSTN to customer's mobile.
  4. Customer's voice flows back the reverse direction.
  5. You hear them through your laptop speakers; they hear you through your laptop microphone.

Visual recap

You speak Browser captures mic | v [DTLS-SRTP] encrypted audio over UDP 16000-16100 | v ASTERISK decrypts, then re-packs for Synchrovox | v [RTP] plain UDP audio | v SYNCHROVOX converts to PSTN format | v PSTN -> Mobile carrier -> Customer hears you

5. The Audio Problem — what was wrong & how it was fixed

For a long stretch of testing, calls would connect but produce complete silence in the browser. Here's the full diagnosis and resolution.

5.1 The symptom

  • Call timer in the browser showed "In call 02:14" — signaling was perfect.
  • Both your phone and the destination's phone rang and answered.
  • But neither side could hear anything — total silence.

5.2 What we proved on the server

Using Asterisk's diagnostic commands:

docker exec asterisk asterisk -rx "pjsip show channelstats"

webrtcuser-0000002  alaw  Receive=9008  Transmit=8947  loss=0  jitter=0
  • 9008 RTP packets received from your mic — browser-to-server direction worked perfectly.
  • 8947 RTP packets sent back to the browser — server was actively pushing audio.
  • Zero packet loss, zero jitter, codec ulaw negotiated.

This proved the network and audio plumbing was fine on the server side. The audio was reaching the browser. It just wasn't reaching the speakers.

5.3 The root cause

Three browser-side problems stacked together:

Cause A — AudioContext at 8 kHz was hijacking the audio

The original code was feeding the WebRTC stream into a Web Audio API AudioContext at 8 kHz sample rate. Most laptop sound cards run at 48 kHz, and Chrome can't drive output at 8 kHz reliably. Also, createMediaStreamSource() "captures" the audio stream and prevents the regular <audio> element from playing it. Two ways the audio was being silenced at once.

Cause B — Chrome autoplay policy blocked playback

The audio.play() call happened inside the WebRTC track event handler — an asynchronous network callback. Chrome doesn't count network callbacks as "user gestures," so it refused to autoplay the audio with a NotAllowedError.

Cause C — Stale React closure on dial number

When the new top "Make a Call" panel triggered the dialer via a window event, the receiving makeCall() function was reading the dial number from React state. But React hadn't yet committed the state update from the event, so the function read an empty string and silently bailed out.

5.4 The fixes

FixWhat it doesFile
Removed the AudioContext tap The <audio> element now handles WebRTC audio directly — nothing else intercepts the stream. portal/src/app/dashboard/calls/page.js
Autoplay priming Calls audio.play() synchronously inside the Call button click handler — Chrome marks the element as user-activated, so later programmatic play works without a gesture. page.js — makeCall()
Visible <audio controls> The audio player is now visible on screen with a play button — even if autoplay fails, the user can manually start it. page.js render
makeCall(dest) parameter override External callers (Make a Call panel) pass the destination directly to makeCall() instead of relying on React state — sidesteps the stale-closure bug. page.js
Window-event bridge The top Make a Call panel dispatches a sipaas:call event; BrowserPhone listens and handles it — keeps the two React components decoupled. page.js
rtp_keepalive=5 on Synchrovox trunk Asterisk now sends silence packets every 5 sec, opening NAT pinholes proactively — helps NAT-traversal for outbound calls. asterisk/conf/pjsip.conf

Result

Internal extensions (100, 200, 300) play crystal-clear audio in the browser. Real PSTN-bound calls work for signaling and the local audio path; the remaining limitation is a network-layer constraint (residential ISP NAT) that no software change can fix — addressed in Section 7.

6. The Call-Setup-Time Problem — investigation & tuning

After fixing audio, real PSTN calls sometimes took 5-10 seconds before the destination phone started ringing. Several optimisations were tried.

6.1 Where the time actually goes

StageTimeControlled by
Browser INVITE → Asterisk< 50 msLocal network
Asterisk dialplan execution< 10 msOur code
Asterisk INVITE → Synchrovox~ 100 msInternet round-trip
Synchrovox routing to Indian PSTN2–8 secondsSynchrovox + telco (outside our control)
Telco delivers to destination handset~ 1 secCarrier (outside our control)

Hard truth

The bulk of the delay (90%+) is PSTN routing at Synchrovox / the destination carrier — nothing in our software causes it, and nothing in our software can speed it up. Indian PSTN routing is just slower than other regions.

6.2 What we did optimise on our side

OptimisationEffect
Removed the +91 internal canonical detour for Indian numbers Saves microseconds — symbolic; final wire output is identical (06265338665).
Direct-dial path in from-webrtc-routed for 10-digit Indian numbers One dialplan hop instead of two. A few milliseconds shaved.
Explicit 30 sec Dial() timeout If destination doesn't answer, we hang up after 30 sec instead of waiting for the default 32-sec SIP timer.
Widened Indian mobile pattern to _[6-9]XXXXXXXXX Reliance Jio's 6XXX prefixes now route correctly (used to be rejected).
RTP keepalive every 5 sec on Synchrovox trunk Faster first-RTP-arrival because NAT pinholes are pre-opened.

6.3 Bottom line

Our share of the call-setup latency is now under 200 ms. The remaining 2–8 sec is Synchrovox routing into the Indian PSTN — not fixable from our end. Internal calls (ext 100/200/300) connect instantly precisely because they never touch Synchrovox.

What requires a public-IP server (VPS)

The single biggest remaining issue

Your laptop sits behind a residential ISP, which blocks inbound UDP packets. Synchrovox's return audio (the destination's voice coming back to you) can't reach your laptop. This is a network-layer constraint — not a code bug.

Fix: Deploy the same Docker stack on a VPS (DigitalOcean, Hetzner, Linode — $5-20/month) with a static public IP. The configuration files already support this; just change the PUBLIC_IP in .env and bring it up. Real PSTN audio will work.

What's in the codebase but unexercised

  • Kamailio + customer-PBX path — all code is wired up (auth, balance, channels) but no external SIP softphone has actually registered through it to validate the flow.
  • Inbound DID call routing — from-synchrovox dialplan exists; no real DID has been provisioned and called.
  • Channel limits, balance enforcement — logic is in Kamailio.cfg; no call has ever hit those checks.
  • RTPEngine — container runs, but doesn't sit in any active call path.

8. Glossary for non-technical readers

TermPlain-English meaning
SIPProtocol for setting up phone calls over the internet. Think of it like HTTP for phones.
RTPThe packets that carry actual voice data once a call is connected.
SDPA small text block inside SIP messages that says "here's where to send audio."
Codec (ulaw, alaw, opus)How audio is compressed for transmission. Like MP3 but for live voice.
NATHow your home router translates many devices behind one public IP. Causes problems for VoIP audio.
CGNAT"Carrier-Grade NAT" — when your ISP itself shares one public IP across many customers. Common in residential India. Blocks most VoIP inbound traffic.
ICE / STUN / TURNTechniques WebRTC uses to discover working network paths through NAT.
DTLS-SRTPEncrypted version of RTP. Used by WebRTC for secure audio.
B2BUA"Back-to-Back User Agent" — an intermediary that terminates one call leg and originates another. Asterisk is doing this between your browser and Synchrovox.
DID"Direct Inward Dial" number — a real phone number anyone can dial to reach your system.
PSTNThe traditional global phone network (landlines + cellular).
SIP TrunkA virtual phone line bound to a username/password — what your customers buy.
CDRCall Detail Record — a database row per call (when, who, how long, cost).
DialplanAsterisk's rulebook for "when this number is dialled, do this."
EndpointA configured SIP identity in Asterisk — like a phone account.
Container / DockerA self-contained box holding one piece of the system + everything it needs to run.
